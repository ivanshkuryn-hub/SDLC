## 1. Введение {#1-introduction}

### 1.1 Назначение документа {#11-document-purpose}

Целью настоящего документа является фиксация бизнес-требований к десктопному приложению NutriTrack, предназначенному для ведения дневника питания и контроля водного баланса. Документ определяет, какие задачи должен решать продукт и какие возможности необходимо предоставить его пользователям. Он предназначен для заказчика, менеджера проекта, разработчиков и специалистов по тестированию и служит основой для дальнейшей разработки системных требований и проектной документации.

### 1.2 Область применения продукта {#12-product-scope}

NutriTrack — это десктопное приложение для персональных компьютеров, позволяющее пользователям вести ежедневный учет потребляемых калорий (БЖУ) и выпитой воды. Продукт позволит добавлять продукты в дневник вручную или с помощью загрузки фотографии штрих-кода, отслеживать прогресс в виде графиков, а также получать напоминания о необходимости питьевой воды.

В первую версию продукта входят:
- Ведение дневника питания с подсчётом калорий и БЖУ.
- Учёт водного баланса (быстрые кнопки и ручной ввод).
- Распознавание продуктов по штрих-коду с загруженного изображения.
- Визуализация прогресса (графики за неделю).
- Система локальных напоминаний о воде.
- Настройка персональных целей.

В первую версию продукта **не входят**: синхронизация с облачными сервисами, интеграция с фитнес-браслетами (Apple Health, Google Fit), социальные функции и функции медицинской диагностики.

### 1.3 Определения, акронимы и сокращения {#13-definitions-acronyms-and-abbreviations}

| Термин | Определение |
|---|---|
| КБЖУ | Калории, Белки, Жиры, Углеводы |

| Дневник | Запись приемов пищи за текущий день |
| Водный баланс | Соотношение выпитой и затраченной жидкости |

Документ состоит из пяти основных разделов. В первом разделе определяются назначение спецификации, область применения продукта и используемая терминология. ## 2. Обзор продукта {#2-product-overview}

### 2.1 Перспектива продукта {#21-product-perspective}

NutriTrack представляет собой новый самостоятельный десктопный продукт, предназначенный для автоматизации процессов контроля питания и водного баланса. До внедрения системы пользователи вынуждены вести записи в бумажных блокнотах или разрозненных таблицах, что затрудняет подсчёт КБЖУ и анализ прогресса. Приложение должно объединить основные этапы учёта в единой информационной системе. Взаимодействие с пользователем осуществляется через графический интерфейс (GUI) на базе Java Swing. Внешние сетевые сервисы и базы данных в первой версии не используются.

Владельцем продукта и заказчиком выступает фитнес-клуб «Здоровье». Управление содержимым (базой продуктов) осуществляется локально в файлах приложения.

### 2.2 Функции продукта {#22-product-functions}

Приложение NutriTrack предоставляет следующие основные функциональные возможности:

- **Учет питания.** Ведение дневника съеденных продуктов с автоматическим подсчетом калорий и БЖУ.
- **Учет воды.** Фиксация выпитой жидкости за день с помощью быстрых кнопок (+250 мл, +500 мл) или ручного ввода.
- **Сканирование штрих-кодов.** Загрузка фотографии штрих-кода продукта для автоматического распознавания и добавления его в дневник.
- **Целеполагание.** Настройка персональных дневных целей по калориям, БЖУ и объему воды.
- **Визуализация.** Построение графиков прогресса за неделю (соотношение выпитой воды и потребленных калорий к целевым значениям).
- **Напоминания.** Выдача системных уведомлений (в трее) о необходимости сделать перерыв и попить воды.

### 2.3 Ограничения продукта {#23-product-constraints}

При разработке первой версии NutriTrack необходимо учитывать следующие ограничения:
- Продукт реализуется в виде **десктопного приложения** для операционных систем Windows/Linux.
- **Технологический стек:** язык Java (версия 17) и библиотека Swing для построения интерфейса.
- **Автономность:** приложение должно работать без подключения к интернету. База продуктов хранится локально в файлах (CSV).
- **Распознавание:** сканирование штрих-кодов осуществляется не через веб-камеру в реальном времени, а путём анализа загруженного пользователем фотоизображения (JPEG/PNG).
- Срок реализации проекта ориентировочно составляет 6 недель.
- Бюджет проекта ограничен, предпочтение отдаётся экономичным решениям (бесплатные библиотеки).

### 2.4 Характеристики пользователей {#24-user-characteristics}

В системе предусматриваются две основные категории пользователей.

| Категория пользователя | Основные характеристики | Предоставляемые возможности |
|---|---|---|
| Пользователь, следящий за весом (любитель) | Человек, желающий похудеть или поддерживать форму. Имеет базовые навыки работы с ПК. | Ввод данных о питании и воде, просмотр графиков, настройка простых целей |
| Спортсмен и фитнес-энтузиаст | Пользователь, которому важен точный контроль БЖУ и водного баланса. | Все возможности любителя, а также детальная статистика и настройка жестких индивидуальных целей |

Пользовательский интерфейс должен быть понятен пользователям с различным уровнем компьютерной подготовки. Для всех категорий необходимо обеспечить простой процесс добавления продуктов и воды.

### 2.5 Допущения и зависимости {#25-assumptions-and-dependencies}

- **Допущения:** Пользователь имеет персональный компьютер с установленной Java 17. Пользователь знаком с основами работы в графических интерфейсах операционных систем. Наличие интернета не требуется.
- **Зависимости:** Для распознавания штрих-кодов используется библиотека ZXing. Для построения графиков — JFreeChart. Для хранения данных — стандартная файловая система.

| Учёт воды | Фиксация выпитой жидкости | Первая версия |
| Сканер штрих-кодов | Загрузка фото и распознавание | Первая версия |
| Графики прогресса | Визуализация статистики | Первая версия |
| Напоминания | Системные уведомления | Первая версия |
| Синхронизация с облаком | Обмен данными между устройствами | За пределами первой версии |
| Интеграция с фитнес-браслетами | Импорт данных о шагах и пульсе | За пределами первой версии |

## 3. Требования {#3-requirements}

### 3.1 Внешние интерфейсы {#31-external-interfaces}

#### 3.1.1 Пользовательские интерфейсы {#311-user-interfaces}

Система должна предоставлять графический интерфейс (GUI) на базе Java Swing, обеспечивающий взаимодействие пользователя с основными функциями. Предусматриваются следующие основные экраны:

| Экран | Назначение |
|---|---|
| Главное окно | Отображение текущего прогресса (калории, вода, стрик) |
| Дневник питания | Список съеденных продуктов, добавление/удаление записей |
| Сканер | Диалог загрузки изображения и отображения результата распознавания |
| Учёт воды | Кнопки быстрого добавления, ползунок объёма |
| Прогресс | Графики за неделю |
| Настройки | Установка целей и напоминаний |

Интерфейс должен быть интуитивно понятным и не требовать от пользователя специальных знаний.

#### 3.1.2 Аппаратные интерфейсы {#312-hardware-interfaces}

Специальные аппаратные интерфейсы не предусмотрены. Для работы с системой пользователю необходим персональный компьютер (или ноутбук) с операционной системой Windows 10+ или Linux, а также стандартные устройства ввода (клавиатура, мышь). Для загрузки фото штрих-кода достаточно файловой системы.

#### 3.1.3 Программные интерфейсы {#313-software-interfaces}

В первой версии NutriTrack предусматривается взаимодействие со следующими программными средствами:
- **Операционная система.** Обеспечивает работу Java-виртуальной машины (JVM) и файловой системы.
- **Библиотека ZXing.** Используется для декодирования изображений штрих-кодов.
- **Библиотека JFreeChart.** Используется для отрисовки графиков.
- **Файловая система.** Используется для хранения базы продуктов (`products.csv`) и записей пользователя (дневник, вода).

### 3.2 Функциональные требования {#32-functional}

#### 3.2.1 Учёт питания

**REQ-FUNC-001 — Добавление продукта вручную**
- **Statement:** Система должна позволять пользователю добавлять продукт в дневник питания вручную, указывая название, вес и калорийность.
- **Rationale:** Обеспечение базовой возможности учёта питания.
- **Acceptance Criteria:** Пользователь может ввести данные в форму и сохранить запись. Запись отображается в списке за текущий день.
- **Verification Method:** Test.

**REQ-FUNC-002 — Автоматический подсчёт КБЖУ**
- **Statement:** Система должна автоматически пересчитывать калории и БЖУ в зависимости от указанного веса продукта.
- **Rationale:** Снижение вероятности ошибок при ручном подсчёте.
- **Acceptance Criteria:** При изменении веса продукта итоговые значения калорий и БЖУ пересчитываются и отображаются в интерфейсе.
- **Verification Method:** Test.

**REQ-FUNC-003 — Просмотр суммарных значений за день**
- **Statement:** Система должна отображать суммарное количество потреблённых калорий и БЖУ за текущий день.
- **Rationale:** Предоставление пользователю сводной информации.
- **Acceptance Criteria:** На главном экране отображается круговая диаграмма (или текст) с итоговыми значениями.
- **Verification Method:** Test.

#### 3.2.2 Учёт воды

**REQ-FUNC-004 — Быстрое добавление воды**
- **Statement:** Система должна предоставлять кнопки для быстрого добавления объёма воды (+250 мл, +500 мл).
- **Rationale:** Упрощение и ускорение процесса логирования.
- **Acceptance Criteria:** При нажатии на кнопку счётчик выпитой воды увеличивается на соответствующее значение.
- **Verification Method:** Test.

**REQ-FUNC-005 — Ручной ввод объёма воды**
- **Statement:** Система должна позволять пользователю вводить произвольный объём воды.
- **Rationale:** Гибкость для разных ситуаций (например, стакан сока).
- **Acceptance Criteria:** Пользователь может ввести числовое значение, которое прибавляется к общему счётчику.
- **Verification Method:** Test.

**REQ-FUNC-006 — Отображение прогресса по воде**
- **Statement:** Система должна отображать шкалу прогресса (0–100%) относительно установленной дневной цели.
- **Rationale:** Визуальная мотивация пользователя.
- **Acceptance Criteria:** Шкала заполняется пропорционально выпитому объёму.
- **Verification Method:** Test.

#### 3.2.3 Сканирование штрих-кодов

**REQ-FUNC-007 — Загрузка фото штрих-кода**
- **Statement:** Система должна предоставлять диалог выбора файла изображения (JPEG/PNG) для загрузки фотографии штрих-кода.
- **Rationale:** Использование фото вместо ручного ввода.
- **Acceptance Criteria:** Пользователь может выбрать файл через стандартный диалог ОС.
- **Verification Method:** Test.

**REQ-FUNC-008 — Распознавание штрих-кода**
- **Statement:** Система должна декодировать загруженное изображение и извлекать строку штрих-кода.
- **Rationale:** Автоматизация ввода данных о продукте.
- **Acceptance Criteria:** Если на изображении есть чёткий штрих-код, система выводит его в виде строки.
- **Verification Method:** Test, Demonstration.

**REQ-FUNC-009 — Поиск продукта в локальной базе**
- **Statement:** Система должна искать распознанный штрих-код в локальном файле `products.csv`.
- **Rationale:** Получение КБЖУ для автоматического заполнения.
- **Acceptance Criteria:** Если продукт найден, отображается его карточка с названием и КБЖУ. Если не найден — выводится сообщение.
- **Verification Method:** Test.

#### 3.2.4 Визуализация прогресса

**REQ-FUNC-010 — Построение графика за неделю**
- **Statement:** Система должна строить график потребления калорий и воды за последние 7 дней.
- **Rationale:** Наглядное отображение динамики.
- **Acceptance Criteria:** На экране «Прогресс» отображается линейный или столбчатый график с данными за неделю.
- **Verification Method:** Demonstration.

#### 3.2.5 Напоминания

**REQ-FUNC-011 — Настройка интервала напоминаний**
- **Statement:** Система должна позволять пользователю задавать интервал (в минутах) для напоминаний о воде.
- **Rationale:** Адаптация под привычки пользователя.
- **Acceptance Criteria:** Пользователь может установить интервал в настройках.
- **Verification Method:** Test.

**REQ-FUNC-012 — Отображение уведомления в трее**
- **Statement:** Система должна периодически показывать системное уведомление в трее с напоминанием о воде.
- **Rationale:** Привлечение внимания без прерывания работы.
- **Acceptance Criteria:** По истечении заданного интервала появляется всплывающее уведомление.
- **Verification Method:** Demonstration.

### 3.3 Качество обслуживания {#33-quality-of-service}

#### 3.3.1 Производительность {#331-performance}

- **REQ-PERF-001 — Время запуска приложения:** Запуск приложения должен занимать не более 3 секунд.
- **REQ-PERF-002 — Время распознавания:** Обработка загруженного изображения и распознавание штрих-кода должны занимать не более 2 секунд.

#### 3.3.2 Безопасность {#332-security}

- **REQ-SEC-001 — Локальность данных:** Все пользовательские данные хранятся только на локальном диске и не передаются по сети.
- **REQ-SEC-002 — Валидация ввода:** Система должна проверять корректность вводимых числовых значений (например, вес не может быть отрицательным).

#### 3.3.3 Надёжность {#333-reliability}

- **REQ-REL-001 — Сохранность данных:** Данные не должны теряться при аварийном завершении работы (запись в файл должна происходить атомарно или с резервным копированием).
- **REQ-REL-002 — Обработка ошибок:** При некорректном изображении штрих-кода система должна выводить понятное сообщение, а не завершаться с ошибкой.

#### 3.3.4 Доступность {#334-availability}

- **REQ-AVAIL-001 — Доступность интерфейса:** Интерфейс приложения должен оставаться отзывчивым во время выполнения фоновых операций (например, распознавания).

#### 3.3.5 Наблюдаемость {#335-observability}

- **REQ-OBS-001 — Логирование ошибок:** Критические ошибки (например, проблемы с чтением файлов) должны записываться в лог-файл для последующего анализа.

### 3.4 Соответствие стандартам {#34-compliance}

- **REQ-COMP-001 — Лицензионная чистота:** Используемые библиотеки (ZXing, JFreeChart) должны иметь свободные лицензии (Apache 2.0, LGPL), допускающие коммерческое использование.

### 3.5 Проектирование и реализация {#35-design-and-implementation}

#### 3.5.1 Установка {#351-installation}

- **REQ-INST-001 — Простая установка:** Приложение должно распространяться в виде исполняемого `.jar` файла. Для запуска достаточно наличия Java 17.

#### 3.5.2 Сборка и поставка {#352-build-and-delivery}

- **REQ-BUILD-001 — Сборка через Maven:** Проект должен собираться с помощью Maven. Должен быть создан исполняемый JAR-файл.

#### 3.5.3 Распределение {#353-distribution}

Не применимо. Приложение не является распределённым.

#### 3.5.4 Сопровождаемость {#354-maintainability}

- **REQ-MAINT-001 — Модульность:** Код должен быть разделён на слои (UI, логика, работа с файлами). Должны соблюдаться принципы ООП.

#### 3.5.5 Повторное использование {#355-reusability}

- **REQ-REUSE-001 — Использование библиотек:** Для сканирования и графиков используются проверенные сторонние библиотеки, что снижает объём собственного кода.

#### 3.5.6 Переносимость {#356-portability}

- **REQ-PORT-001 — Кроссплатформенность:** Приложение должно работать в Windows 10+ и Linux (например, Ubuntu 20.04+).

#### 3.5.7 Стоимость {#357-cost}

Бюджет проекта ограничен. Используются только бесплатные инструменты и библиотеки.

#### 3.5.8 Сроки {#358-deadline}

Проект должен быть завершён в течение 6 недель с момента начала разработки.

#### 3.5.9 Доказательство концепции {#359-proof-of-concept}

- **REQ-POC-001 — Прототип сканера:** На ранних этапах необходимо создать прототип, подтверждающий возможность распознавания штрих-кода с фото с помощью ZXing.

#### 3.5.10 Управление изменениями {#3510-change-management}

- **REQ-CM-001 — Контроль версий:** Изменения в коде и документации должны фиксироваться в Git.

### 3.6 ИИ/МО {#36-aiml}

Не применимо. В первой версии продукта не используются модели машинного обучения или искусственный интеллект.

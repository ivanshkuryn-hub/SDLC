# Описание дизайна программного обеспечения (SDD) — NutriTrack

**Версия:** 1.0  
**Статус:** Проектная редакция  
**Дата:** 19.11.2026  
**Основание:** SRS NutriTrack 0.3 и системные требования NutriTrack 0.3

## 1. Введение

### 1.1 Назначение документа

Документ описывает проектируемую архитектуру и дизайн локального веб-приложения NutriTrack: архитектурный стиль, программные компоненты, их ответственность и взаимодействие, структуру данных, пользовательский интерфейс, основные операции и развёртывание.


### 1.2 Область проектирования

NutriTrack — локальное веб-приложение для персонального компьютера. Оно предназначено для ежедневного учёта калорий, дополнительного отображения белков, жиров и углеводов (БЖУ), учёта выпитой воды, распознавания штрих-кодов по загруженным изображениям, контроля массы тела, экспорта дневника питания в PDF и визуализации прогресса. Серверная часть и браузер работают на одном компьютере. Адрес приложения: `http://localhost:8080`.

### 1.3 Связанные документы

- SRS NutriTrack версии 0.3.
- Системные требования NutriTrack версии 0.3.
- `docs/design/gui_mockup_4_screens.png`.
- `docs/design/gui_mockup_4_screens.sysml`.
- ADR-0001 — ZXing для распознавания штрих-кодов.
- ADR-0002 — файловое хранилище CSV/TXT.
- ADR-0003 — локальное веб-приложение Spring Boot, Spring MVC и Thymeleaf.
- ADR-0004 — напоминания о воде отложены и не входят в первую версию.

## 2. Обзор архитектуры

### 2.1 Архитектурный стиль

Выбирается слоистая архитектура с разделением ответственности между представлением, обработкой веб-запросов, бизнес-логикой и доступом к данным. Взаимодействие браузера с сервером организуется по модели MVC (Model–View–Controller) средствами Spring MVC.

Основные слои:

- **Presentation Layer:** HTML-страницы, шаблоны Thymeleaf, CSS и элементы управления.
- **Web/Controller Layer:** приём HTTP-запросов, проверка параметров, вызов сервисов и подготовка ответа.
- **Service/Domain Layer:** расчёты КБЖУ, обработка дневника питания и воды, управление целями, распознавание штрих-кодов, графики, контроль веса и экспорт PDF.
- **Repository/Data Access Layer:** чтение и запись CSV и Properties.
- **Model Layer:** модели продуктов, записей питания, воды и настроек.

Слои являются логическими частями одного приложения. Микросервисы и раздельное развёртывание компонентов не предусматриваются.

### 2.2 Контекстное представление (Context View)

Пользователь открывает `http://localhost:8080` в браузере. Браузер отправляет HTTP-запросы локальному серверу Spring Boot. Контроллеры обрабатывают запросы и обращаются к сервисам. Сервисы выполняют бизнес-операции и используют репозитории для работы с локальными файлами. Сервер возвращает HTML-страницы, сформированные Thymeleaf, и необходимые данные для отображения интерфейса.

Внешние облачные сервисы, удалённые базы данных и сторонние API не используются. Работа приложения не должна требовать подключения к интернету. Статические ресурсы интерфейса хранятся в составе приложения.

### 2.3 Композиционное представление (Composition View)

| Компонент | Назначение |
|---|---|
| Web Interface | Отображение четырёх экранов, форм, карточек, графиков, прогресса и PDF-экспорта |
| Spring MVC Controllers | Приём запросов, проверка входных данных, вызов сервисов и подготовка представлений |
| Food Service | Добавление и удаление записей питания, организация расчёта КБЖУ и обновление дневных итогов |
| Nutrition Service | Расчёт калорий и БЖУ для фактической массы порции |
| Water Service | Добавление воды, расчёт дневного объёма и прогресса |
| Goal and Settings Service | Управление дневными целями и темой |
| Barcode Service | Распознавание штрих-кода с помощью ZXing |
| Product Service | Поиск продукта в `products.csv` и подготовка карточки |
| Chart Service | Подготовка данных за семь дней и формирование PNG-графиков калорий, воды и массы тела через JFreeChart; выдача изображений через локальные HTTP-маршруты |
| Weight Service | Проверка и сохранение измерений массы тела, подготовка данных для графика |
| PDF Report Service | Формирование PDF-отчёта по дневнику питания за выбранную дату |
| Repositories | Чтение и запись локальных файлов |

Контроллеры связывают веб-представление с сервисами. Сервисы не должны непосредственно формировать HTML-разметку. Репозитории изолируют файловые операции от бизнес-логики.

Назначение пакетов:

- `controller` — контроллеры Spring MVC для обработки запросов экранов.
- `service` — прикладная логика и операции предметной области.

- `model` — модели данных.
- `config` — конфигурация приложения и веб-компонентов.

### 2.5 Представление пользовательского интерфейса (User Interface View)

Интерфейс состоит из четырёх основных экранов. Общая навигация и переключатель светлой/тёмной темы доступны в общей части интерфейса.

#### 2.5.1 Главная (DashboardScreen)

Экран отображает сводку за текущий день и динамику за последние семь дней:

- суммарное количество потреблённых калорий;
- суммарные значения белков, жиров и углеводов;
- дневную цель по калориям, её настройку и прогресс;
- прогресс потребления воды относительно дневной цели;
- графики калорий и воды за последние семь дней;
- график изменения массы тела и форма добавления измерения веса;
- общую навигацию;
- переключатель светлой и тёмной темы.

БЖУ являются дополнительной информацией. Отдельные дневные цели и графики БЖУ не предусматриваются.

#### 2.5.2 Дневник питания (FoodDiaryScreen)

Экран предназначен для просмотра и изменения записей о съеденных продуктах за выбранную дату (по умолчанию — текущий день):

- выбор даты дневника и список продуктов за выбранную дату (по умолчанию — текущий день);
- форма ручного добавления;
- ввод названия и фактического веса порции;
- ввод калорийности и БЖУ на 100 г при ручном добавлении;
- отображение рассчитанных значений для порции;
- удаление выбранной записи;
- суммарные значения калорий и БЖУ за день;
- экспорт дневника питания за выбранную дату в PDF.

#### 2.5.3 Сканер (ScannerScreen)

Экран предназначен для распознавания штрих-кода по загруженному изображению:

- выбор локального изображения JPEG или PNG;
- передача изображения серверной части для обработки ZXing;
- отображение распознанной строки;
- поиск продукта в `products.csv`;
- отображение карточки найденного продукта;
- ввод фактического веса съеденного продукта и отображение рассчитанных значений КБЖУ для указанной порции;
- подтверждение добавления рассчитанной порции в дневник питания;
- предложение ручного ввода, если продукт отсутствует в базе.

Сканирование камерой в реальном времени не предусматривается.

#### 2.5.4 Учёт воды (WaterScreen)

Экран предназначен для регистрации выпитой воды и настройки водного баланса:

- быстрое добавление 250 мл и 500 мл;
- ручной ввод объёма;
- отображение дневного объёма;
- настройка дневной цели по воде;
- отображение прогресса;




### 2.6 Информационное представление (Information View)

#### 2.6.1 Общие принципы

Пользовательские данные хранятся локально. В первой версии используются CSV и Properties. СУБД не применяется.

Предлагаемая структура каталога:

```text
data/
├── products.csv
├── settings.properties
├── meals/
│   └── YYYY-MM-DD.csv
├── water/
│   └── YYYY-MM-DD.csv
└── weight.csv
```

Каталог пользовательских данных отделяется от временных файлов сборки и ресурсов приложения, чтобы пересборка или обновление JAR не удаляли дневники и настройки.

#### 2.6.2 База продуктов

Файл `products.csv` содержит поля:

```text
barcode,name,kcal,protein,fat,carbs
```

| Поле | Описание |
|---|---|
| `barcode` | Строковое значение штрих-кода |
| `name` | Название продукта |
| `kcal` | Калорийность на 100 г |
| `protein` | Белки на 100 г |
| `fat` | Жиры на 100 г |
| `carbs` | Углеводы на 100 г |

Штрих-код обрабатывается как строка, чтобы сохранять возможные ведущие нули.

#### 2.6.3 Дневник питания

Для каждого дня используется файл `meals/YYYY-MM-DD.csv`. Запись должна содержать дату, идентификатор или штрих-код продукта, название продукта, фактический вес порции и данные о питательной ценности, необходимые для отображения записи и восстановления дневных итогов. Точный разделитель и окончательный состав полей фиксируются при реализации формата хранения. Формат должен корректно обрабатывать названия продуктов и числовые значения.

#### 2.6.4 Учёт воды

Для каждого дня используется файл `water/YYYY-MM-DD.csv`. Каждая запись содержит дату или время и добавленный объём воды в миллилитрах. Дневной объём рассчитывается как сумма записей за соответствующую дату.

#### 2.6.5 Настройки

Файл `settings.properties` хранит:

- дневную цель по калориям;
- дневную цель по воде;
- выбранную цветовую тему.

Настройки загружаются при запуске и сохраняются после изменения пользователем.

### 2.7 Представление взаимодействия (Interaction View)

#### 2.7.1 Добавление продукта вручную

- Пользователь открывает дневник питания и выбирает ручное добавление продукта.
- Web Interface отображает форму ввода данных продукта.
- Пользователь вводит название продукта, фактический вес порции, калорийность и значения БЖУ на 100 г.
- FoodDiaryController принимает запрос и проверяет корректность входных данных.
- FoodService организует добавление продукта и обращается к NutritionService для расчёта КБЖУ фактической порции.
- NutritionService возвращает рассчитанные значения калорий, белков, жиров и углеводов.
- FoodService передаёт сформированную запись в MealRepository для сохранения в дневном файле выбранной даты.
- При успешном сохранении система обновляет дневные итоги и возвращает обновлённую страницу дневника.
- При некорректных данных или ошибке сохранения система отображает понятное сообщение и продолжает работу.

#### 2.7.2 Расчёт КБЖУ

Для каждого показателя применяется формула:

\[
N_{порции} = \frac{N_{100г} \times m}{100}
\]

где `Nпорции` — значение показателя в порции, `N100г` — значение на 100 г, `m` — фактический вес порции в граммах.

Дневные итоги формируются суммированием значений всех записей за выбранную дату. Отдельные цели по БЖУ не рассчитываются.

#### 2.7.3 Учёт воды

- Пользователь выбирает добавление 250 мл, 500 мл или ручной ввод.
- Контроллер передаёт значение сервису учёта воды.
- Сервис проверяет, что объём является положительным числом.
- Репозиторий сохраняет запись в дневном файле воды.
- Сервис рассчитывает общий объём и прогресс относительно дневной цели.
- Контроллер возвращает обновлённые данные экрану.

#### 2.7.4 Распознавание штрих-кода

- Пользователь выбирает изображение JPEG или PNG.
- Контроллер принимает файл и проверяет его наличие и тип.
- Barcode Service передаёт изображение библиотеке ZXing.
- ZXing возвращает строку штрих-кода либо результат отсутствия распознавания.
- Product Service ищет код в `products.csv`.
- При совпадении интерфейс отображает карточку продукта с данными на 100 г.
- После указания фактического веса съеденного продукта система рассчитывает значения КБЖУ для указанной порции.
- Пользователь подтверждает добавление рассчитанной порции в дневник питания; Food Service сохраняет запись в дневном файле текущей даты через MealRepository.
- При отсутствии совпадения интерфейс предлагает ручной ввод.
- При ошибке загрузки или распознавания отображается понятное сообщение.

#### 2.7.5 Построение графиков

Chart Service получает дневные итоги калорий и воды за последние семь дней и формирует графики с помощью JFreeChart в формате PNG. Сервер предоставляет изображения через локальные HTTP-маршруты, например `/charts/calories.png` и `/charts/water.png`. Weight Service получает сохранённые измерения массы тела и передаёт их Chart Service для формирования отдельного графика изменения веса. Thymeleaf-шаблон главной страницы включает адреса графиков в элементы изображения (`img`), после чего браузер загружает PNG с локального сервера. Графики БЖУ не предусматриваются.

#### 2.7.6 Учёт массы тела

Пользователь вводит значение массы тела и дату измерения. Weight Service проверяет корректность значения и передаёт запись WeightRepository для сохранения в локальном `weight.csv`. При открытии главной страницы сохранённые измерения передаются Chart Service для построения графика изменения веса.

#### 2.7.7 Экспорт дневника питания в PDF

Пользователь выбирает дату и запускает экспорт дневника. Report Service получает записи за выбранную дату через Food Service и формирует PDF-отчёт со списком продуктов, весом порций, рассчитанными значениями калорий и БЖУ и дневными итогами. Сформированный файл передаётся браузеру для сохранения на локальный компьютер.

#### 2.7.8 UML-моделирование взаимодействия

Для представления поведения и взаимодействия компонентов NutriTrack используются UML-диаграммы.

Диаграмма активности (`activity_diagram.png`) отражает общий процесс работы пользователя с приложением, основные функциональные возможности и взаимодействие с системой.

Диаграмма состояний (`state_diagram.png`) описывает состояния основных экранов приложения и переходы между ними.

Диаграмма последовательности (`sequence_diagram.png`) отражает порядок взаимодействия пользователя, веб-интерфейса, контроллеров, сервисов и репозитория при ручном добавлении продукта в дневник питания.

Исходные модели диаграмм представлены в формате PlantUML и хранятся в каталоге `docs/design/`.

### 2.8 Представление развертывания (Deployment View)

NutriTrack развёртывается на одном персональном компьютере. Среда выполнения включает:

- Java 17;
- исполняемый JAR-файл, собранный Maven;
- встроенный веб-сервер Spring Boot;
- современный браузер;
- локальный каталог пользовательских данных.

После запуска JAR сервер доступен по адресу `http://localhost:8080`. Приложение не предназначено для публикации в интернете или обслуживания удалённых клиентов.

### 2.9 Безопасность и надёжность

Архитектура должна обеспечивать следующие свойства:

- пользовательские данные хранятся только на локальном диске;
- передача пользовательских данных за пределы компьютера не выполняется;
- сервер доступен через `localhost`;
- числовые значения и загружаемые изображения проверяются до передачи в бизнес-логику;
- ошибка отдельной операции не должна приводить к аварийному завершению приложения;
- ошибки чтения и записи файлов фиксируются в журнале;
- запись данных выполняется способом, снижающим риск повреждения файла при прерывании операции;
- каталог пользовательских данных не удаляется при обычной пересборке приложения.

### 2.10 Представление тестирования

Проверка проектируемой системы должна включать модульные и интеграционные тесты, а также проверку пользовательских сценариев.

Основные направления:

- добавление и удаление записей питания;
- расчёт калорий и БЖУ для разных весов порций;
- формирование дневных сумм;
- быстрое и ручное добавление воды;
- расчёт прогресса по воде;
- сохранение и загрузка дневных целей и темы;
- загрузка JPEG/PNG и распознавание поддерживаемых штрих-кодов;
- поиск продукта, подтверждение добавления найденного продукта в дневник и сценарий отсутствующего продукта;
- выбор даты дневника и сохранение записей за выбранную дату;
- формирование графиков калорий и воды за семь дней;
- сохранение измерений массы тела и формирование графика веса;
- формирование и сохранение PDF-отчёта дневника питания;
- обработка ошибок файлов и некорректного ввода;
- запуск приложения и доступность главной страницы.

## 3. Архитектурные ограничения и принципы реализации

### 3.1 Технологический стек

| Технология | Назначение |
|---|---|
| Java 17 | Основной язык и среда выполнения |
| Spring Boot | Конфигурация и запуск локального веб-приложения |

| JUnit | Автоматизированное тестирование |

### 3.2 Ограничения первой версии

В первой версии не предусматриваются:

- Java Swing и JavaFX;
- сканирование веб-камерой в реальном времени;
- удалённая база данных или отдельный сервер СУБД;
- облачная синхронизация;
- интеграция с Apple Health и Google Fit;
- социальные функции и медицинская диагностика;
- отдельные цели и графики по БЖУ;
- React и отдельный SPA-фреймворк;
- Docker и микросервисное развёртывание.

### 3.3 Принципы расширения

Новые функции добавляются с сохранением разделения на контроллеры, сервисы, модели и репозитории. Изменения форматов файлов сопровождаются проверкой совместимости с сохранёнными данными. Изменения архитектуры и технологического стека фиксируются в ADR и согласуются с SRS.

## 4. Архитектурные решения

- **ADR-0001:** Использование ZXing для распознавания штрих-кодов.
- **ADR-0002:** Файловое хранилище CSV/TXT вместо СУБД.
- **ADR-0003:** Локальное веб-приложение на Spring Boot, Spring MVC и Thymeleaf.
- **ADR-0004:** Напоминания о воде отложены и не входят в первую версию.
